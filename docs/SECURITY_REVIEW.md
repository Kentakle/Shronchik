# Проверка защиты Shronchik — 07.11.2026

Проверка выполнена по исходникам и HTTP-запросами к отдельной синтетической библиотеке на loopback. Рабочая медиатека, роутер и публичные адреса не атаковались. Внешний HTTPS-режим остаётся отложенным по решению владельца. Текущий пароль рабочего Admin не менялся.

Это ограниченная проверка приложения, а не независимый аудит криптографии или доказательство отсутствия уязвимостей. Отдельно нужно проверить готовую внешнюю установку, актуальность native-компонентов и восстановление после аварий.

## Подтверждённые проблемы и исправления

| Проблема | Доказательство и влияние | Исправление |
|---|---|---|
| Неограниченно большой JSON относительно назначения API, средняя серьёзность | До исправления общий предел 1 ТиБ действовал и для входа. Синтетический неавторизованный JSON размером 100 030 байт возвращал `401`, то есть проходил чтение и привязку модели вместо отказа по размеру. Проверка не доводилась до исчерпания памяти. | Предел 64 КиБ для обычных запросов до десериализации; для обложки 4 МиБ; 1 ТиБ оставлен только потоковому импорту. Обычные и chunked-запросы сверх лимита получают `413`. |
| Неограниченная очередь проверки паролей, средняя серьёзность | Дорогая операция KDF была сериализована, но число ожидающих уже разобранных запросов не ограничивалось. | Не более 32 запросов на выполнение и ожидание операций аккаунтов; превышение получает `429`. Воспроизведён всплеск из 64 запросов, ответы `200`/`429`, без ошибок сервера. |
| Неограниченное число сеансов после успешного входа, средняя серьёзность при наличии пароля | Клиент мог каждый раз не присылать старую cookie, сохраняя на сервере всё новые сеансы с копиями ключа до 24 часов. | Максимум 16 сеансов аккаунта и 256 суммарно. Самые старые отзываются, их запросы отменяются, принадлежащий сеансу ключ очищается. |
| Неограниченное накопление контекстов просмотра, средняя серьёзность при наличии аккаунта | Общий словарь сохранял маркеры до четырёх часов и обходился целиком при каждом открытии видео. | Маркеры принадлежат сеансу, максимум 128 на сеанс. Старые вытесняются, срок четыре часа проверяется и при использовании, отзыв сеанса удаляет маркеры. Открытие видео больше не сканирует маркеры всех пользователей. |
| Быстрый ответ для отсутствующего или отключённого логина, низкая серьёзность | Эта ветка пропускала Argon2, поэтому заметно отличалась от проверки неправильного пароля существующего аккаунта. | Для этой ветки тоже выполняется KDF; отдельный заведомо неподходящий AAD гарантирует отказ даже при вводе действующего пароля Admin под чужим именем. Это убирает быстрый путь, но не все различия поведения ограничителя попыток, см. ниже. |
| Заголовки защиты исчезали при обработке ошибок, низкая серьёзность | Очистка ответа перед JSON-ошибкой удаляла ранее заданные заголовки. | Применение `no-store`, `nosniff`, CSP, запрета встраивания и CORP перед отправкой ответа, включая ошибки. |

В реализации лимита тела использована [документированная возможность Kestrel задавать предел на запрос до чтения тела](https://learn.microsoft.com/aspnet/core/mvc/models/file-uploads#per-request-body-size-limits). Сопоставимая обработка ошибок входа соответствует [рекомендациям OWASP по отсутствующим, отключённым аккаунтам и времени ответа](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-and-error-messages).

## Что проверено запросами

- Отказ в чтении каталога, тегов, настроек, альбомов, аккаунтов, корзины и сведений о диске без сеанса.
- Подделка роли при входе; попытки обычного аккаунта создать, отключить, удалить или сбросить другой аккаунт, импортировать файл, изменить административные настройки.
- Подмена `Origin`, отсутствие CSRF-токена, `Origin: null`, посторонний `Host` для имитации DNS rebinding.
- Чтение, переименование, удаление и изменение состава альбома по чужому UUID.
- SQL-подобные строки в поиске, названии файла и альбома остаются данными; фильтры не расширяются до всех записей.
- Догадки о путях манифеста, БД и существующего зашифрованного оригинала, пути с `..` и кодированным разделителем. Ответы не содержат эти файлы.
- Случайная cookie, заблокированный и вышедший сеансы не читают защищённые данные. Сеанс другого пользователя не принимает чужой маркер просмотра.
- Заголовки запрета кэширования, CSP, CORP и `nosniff` присутствуют на медиа и ошибках.
- Превышение размеров тела, обход лимита через chunked, всплеск входов и переполнение квот сеансов и маркеров просмотра.

`node tests/security-smoke.mjs`: 9 HTTP-сценариев. Проверки сеансов дополнены до 33. Существующие 20 HTTP-сценариев также прошли после изменений, включая HTTPS-прокси, права, отзыв потоков, смену паролей и удаление аккаунта.

Для отдельного запуска сначала соберите сервер, затем выполните `node tests/security-smoke.mjs` из корня проекта. Сценарий сам запускает и останавливает сервер на 5281 с новой библиотекой в `.cache/security-smoke`. Общая команда `./scripts/test.ps1` включает этот сценарий. Если порт занят, задайте `SHRONCHIK_SECURITY_PORT`.

Дополнительно выполнен `tests/xss-browser-smoke.cjs` в реальном headless Edge через Playwright, на отдельном сервере 5282 и нейтральном PNG. В сохранённые название, собственный тег и имя альбома переданы HTML/script-последовательности с обработчиками `onerror`/`onload` и маркером исполнения. Все три сценария прошли: после перезагрузки галерея, плеер, список альбомов, заголовок альбома и его карточки выводят строки буквально. Атакующие DOM-элементы не появились, маркер исполнения остался нулём, диалогов и JavaScript-ошибок не было. Это подтверждает проверенные места вывода, а не полное отсутствие всех возможных XSS.

Для повторения задайте `SHRONCHIK_PLAYWRIGHT` равным пути к установленному пакету Playwright и выполните `node tests/xss-browser-smoke.cjs` после сборки сервера и UI. По умолчанию используется установленный Edge; путь можно задать через `SHRONCHIK_BROWSER`, порт — через `SHRONCHIK_XSS_PORT`. Тест создаёт новую синтетическую библиотеку в `.cache/xss-browser-smoke` и останавливает только свой сервер. Он запускается отдельно от основного набора, поскольку требует браузер и Playwright.

## Остаточные риски и решения для следующего этапа

1. **До подключения из Интернета:** отдельные ограничения скорости и числа соединений на прокси, наблюдение за неудачными входами и реальная проверка через другую сеть. Ограниченные очереди приложения не защищают от насыщения домашнего канала.
2. **Ограничитель входа:** неизвестные имена делят один счётчик задержки. Это сохраняет ограничение памяти, но может раскрывать различия между существующими и отсутствующими именами и позволяет временно мешать входам. Нужна отдельная схема ограничений по доверенно полученному адресу клиента и аккаунту, с ограниченным хранилищем счётчиков. Обход прав из этого не получен.
3. **Native-зависимости:** результат npm/NuGet-сканирования сам по себе не подтверждает отсутствие проблем в поставляемых SQLite/SQLCipher DLL. Нужна проверка фактических версий, поддерживаемого обновления, лицензий и SBOM.
4. **Восстановление и диск:** recovery-пакет, согласованная резервная копия, аутентификация манифеста, аварийный импорт и миграция пока не закрыты. Для этих сценариев нужны отдельные испытания со сбоями на синтетических копиях.
5. **Права пользователя и копирование медиа:** отсутствие отдельной кнопки или API экспорта не мешает авторизованному браузеру сохранить уже полученные для просмотра байты. Для друзей нужно исходить из доверия к тем, кому предоставлен просмотр.
6. **Граница квот:** после более чем 128 одновременно/последовательно открытых контекстов в одном сеансе самые старые маркеры теряются. Их старый запрос учёта просмотра вернёт `404`; само потоковое воспроизведение от этого не прекращается. Абсолютный срок сеанса — 24 часа, серверная очистка с периодом пять секунд.

Рекомендации не включались автоматически: публичный доступ и текущая схема прав сохранены по последним решениям владельца.
